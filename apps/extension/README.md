# BTU Classroom inspection and browser-assisted checks (Phase 6B)

This Manifest V3 extension inspects only the active BTU Classroom **Groups** page when the user clicks **Inspect this page**. It accepts the exact HTTPS route `/ge/student/me/course/groups/{btuCourseId}/{opaqueRouteParam}` on `classroom.btu.edu.ge`. The first segment is BTU's observed course ID and stays a string; the second segment's meaning is unknown and is not modeled. The My Courses list (`/ge/student/me/index/3`), ordinary subject pages, and Syllabus are not Groups pages.

The popup asks the extension service worker to inspect the active tab. The worker validates the URL, fetches that exact page with `credentials: "include"` and `redirect: "manual"`, and calls the existing `@btu-course-watch/classroom-parser` on the returned HTML. This asks Chrome to use the student's existing Classroom authentication; the extension never reads passwords, cookies, session tokens, or authorization headers. HTML exists only transiently in the worker and is not logged, stored, messaged to the popup, or sent to the BTU Course Watch API. Only a structured `CourseObservation` or a fixed error code reaches the popup. The popup shows whether a Choose action exists but never shows or follows its URL.

After explicit linking, the worker submits only that structured observation to the Course Watch API, then loads the linked user's watch state from the server. The popup offers Watch/Watching controls for displayed groups only after successful ingestion; watch mutations are followed by a server refresh, never a local watch-state cache. It uses a separate random 90-day Course Watch credential scoped to observation submission and the owning user's watches, stored in `chrome.storage.local` (trusted extension contexts only), never the website's HttpOnly cookies. Course Watch requests use `credentials: "omit"`; Classroom requests still use `credentials: "include"` locally. No raw HTML or Classroom credentials are persisted or transmitted to the Course Watch API. A failed submission does not hide the local inspection result, but watch management requires successful ingestion. Watching is separate from observed availability and never enrolls a student.

The development manifest grants only named permissions `storage` and `alarms`, plus exact hosts `https://classroom.btu.edu.ge/*` and `http://localhost:3001/*`. It has no `activeTab`, `tabs`, `cookies`, `scripting`, notifications, or wildcard host permission. `chrome.tabs.create` opens only the fixed Course Watch web approval page and needs no `tabs` permission.

## Build configuration and security

`pnpm --filter @btu-course-watch/extension build` produces a localhost development manifest. For production, set `BCW_API_ORIGIN` and `BCW_WEB_ORIGIN` to exact HTTPS origins (see `.env.production.example`), then run `pnpm --filter @btu-course-watch/extension build:production`; the manifest includes only the configured API host. These are public origins, not secrets. Check `dist/manifest.json` before packaging. A stable published Chrome extension ID may require a packaging key/Chrome Web Store distribution; unpacked IDs can differ. The server binds each link to the runtime extension ID but does not trust that ID alone as authentication. It also requires explicit web approval, a one-time verifier, and a scoped credential. Deploy edge/IP rate limits on public link initiation and exchange routes; no Redis or queue is added here.

The popup initiates a five-minute link request with a SHA-256 challenge for a locally generated random verifier. Only the request ID appears in the trusted website URL. Match the six-character pairing code in the popup and website, then approve while signed in to Course Watch. The extension exchanges the verifier once for a 90-day random credential. The API stores only its SHA-256 hash. Relinking the same installation revokes its previous credential; the user can revoke active authorizations at `/extension-link`. Expiry/revocation requires relinking; there is no silent refresh. Only the dedicated extension status, structured-observation, and owner-scoped watch routes accept this credential. Never paste it into the website or a URL.

Uninstalling the extension removes its local credential but does not by itself revoke the server record; revoke from `/extension-link` before uninstalling if you want immediate server-side invalidation.

## Manual test with your own BTU account

1. Run `pnpm install --frozen-lockfile`, start PostgreSQL, apply API migrations, then run the API on `http://localhost:3001` and web app on `http://localhost:3000`. Build the extension with `pnpm --filter @btu-course-watch/extension build`.
2. In Chrome, open `chrome://extensions`, enable **Developer mode**, click **Load unpacked**, and select `apps/extension/dist`. Reload the extension there after each rebuild.
3. Sign in to the Course Watch web app. Open the extension, choose **Connect Course Watch**, and confirm the popup's pairing code matches the trusted `http://localhost:3000/extension-link` approval page. Approve, return to the popup, and choose **Check authorization**. It should report linked. If not already signed in, the page opens `/login` in another tab; finish login, return, and choose **Check account** before approving.
4. In a separate normal Chrome tab, sign in to BTU Classroom normally. Open **My Courses**, open a specific subject, then select **Groups**. The URL should match `https://classroom.btu.edu.ge/ge/student/me/course/groups/<course ID>/<opaque segment>`.
5. Open the extension and click **Inspect this page**. Confirm the local groups and a distinct “structured observation submitted” result. In the Course Watch website's authenticated browser console, request `GET http://localhost:3001/api/v1/courses/<course ID>` with `credentials: "include"` and verify canonical state. No Choose URL is opened.
6. Visit `http://localhost:3000/extension-link` while signed in and **Revoke** the authorization. Attempt another extension inspection: local groups should still display, but submission should require relinking. Link again and confirm submission resumes.
7. On a random website, expect a non-Classroom error. On My Courses or Syllabus, expect unsupported Groups-page guidance. On `/ge/login` or after Classroom logout, expect a session-required error. When selection mode is disabled, groups should show `UNKNOWN` with no Choose action; quota-full groups show `FULL`.

## Phase 6B automatic observation test (courses 665 and 672)

1. Keep Chrome, the Course Watch API/web app, and your normal BTU Classroom session running. Link the extension, manually inspect Groups pages for courses `665` and `672`, and Watch a displayed group in each. Then leave those pages or close their tabs: automatic checks do **not** need Groups tabs open.
2. Reload the built extension at `chrome://extensions`. Its one alarm starts after approximately 30–35 minutes (the 30-minute cadence plus one small installation jitter). Optionally use the extension's **service worker** inspector to run `chrome.alarms.get("course-watch-observations")` and confirm one 30-minute repeating alarm exists; close DevTools before testing normal worker suspension. Do not alter the alarm or run BTU fetches from the console.
3. After a scheduled cycle, reopen the popup. **Browser-assisted checks** should show the last automatic attempt and successful observation separately from manual **Inspect this page**. On `/watches`, last-observed timestamps for the watched groups should advance. With both watched groups in the same course, the worker sends one subject-page and one Groups-page request for that course per successful cycle; with courses 665 and 672, it does this once per course.
4. Sign out of BTU Classroom (leave Course Watch linked), wait for the next scheduled cycle, and confirm the popup reports BTU sign-in required. BTU traffic pauses for two hours before a probe; a failed check does not advance last successful observation. Sign back in and wait for the next eligible check. A missing or ambiguous Groups link should instead report route discovery unavailable.
5. Revoke the Course Watch extension link at `/extension-link`, then wait for a cycle: it must make no Classroom requests and report that linking is required. Manual local **Inspect this page** still works independently. Re-link for further tests; clear watches afterward if you want the development account clean.

Manual evidence confirms that authenticated **response HTML** for subject pages `/ge/student/me/course/index/665` and `/672` exposes their matching Groups anchors; two students saw the same Groups paths and the same course-665 group catalogue while selection was disabled. The second route segment remains opaque and is discovered anew each cycle, never stored or derived. Browser-assisted checks process at most four distinct courses sequentially per cycle and rotate larger watch lists. A successful cycle means at least one structured observation was accepted; per-course failures remain visible. The worker parses network responses, not rendered tab DOM, so unrelated extension-injected rating badges are not inputs. Raw Classroom HTML and credentials stay in the browser.

Chrome alarms are best effort: sleeping/closed Chrome or an offline device cannot check, events may be delayed, and an expired Classroom session prevents checks. The 30-minute interval is an initial load-conscious setting, **not** a live or 24/7 promise. Multiple devices can submit duplicates; Phase 5A resolves stale/equal observations. Retest whether definitive AVAILABLE/FULL states agree across students during an active selection period before any future alerts rely on globally shared canonical state. True 24/7 monitoring requires separate investigation of a legitimate BTU server-accessible API/webhook or scoped institution-approved integration, never student passwords, cookies, or sessions.
