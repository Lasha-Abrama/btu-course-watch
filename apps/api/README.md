# BTU Course Watch API

NestJS 12, TypeScript 6, ESM, Vitest, and Prisma API workspace.

Copy `.env.example` to `.env`, configure an SMTP server, start the repository PostgreSQL service with `docker compose up -d`, apply the migration with `pnpm --filter api exec prisma migrate deploy`, then run `pnpm --filter api start:dev` from the repository root.

- Health: `GET http://localhost:3001/api/v1/health`
- Swagger UI: `http://localhost:3001/api/docs`
- OpenAPI JSON: `http://localhost:3001/api/docs/openapi.json`
- Registration: `POST /api/v1/auth/register`
- Email verification: `POST /api/v1/auth/verify-email`
- Resend verification: `POST /api/v1/auth/resend-verification`
- Password recovery: `POST /api/v1/auth/forgot-password`, `POST /api/v1/auth/reset-password`
- Password login: `POST /api/v1/auth/login`
- Google sign-in: `GET /api/v1/auth/google` (callback: `GET /api/v1/auth/google/callback`)
- Session renewal/logout: `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout`
- Current user: `GET /api/v1/users/me`
- Structured Groups-page ingestion: `POST /api/v1/observations` (access cookie + trusted origin)
- Shared last-known course state: `GET /api/v1/courses/:btuCourseId` (access cookie)
- Owned watches: `GET /api/v1/watches`, `PUT /api/v1/watches` (`{ "btuCourseId": "665", "btuGroupId": "13344" }`), `DELETE /api/v1/watches/:watchId` (web access cookie; mutations retain origin/CSRF protection)
- Durable availability alerts: `GET /api/v1/notifications` (optional `limit` 1–50 and owned `cursor` UUID), `PUT /api/v1/notifications/:notificationId/read`, `PUT /api/v1/notifications/read-all` (web access cookie; mutations retain origin/CSRF protection). Alerts are historical observations, not live availability.
- Extension link review/approval/list/revocation: `GET /api/v1/extension/link-requests/:requestId`, `POST /api/v1/extension/link-requests/:requestId/approve`, `GET /api/v1/extension/authorizations`, `POST /api/v1/extension/authorizations/:authorizationId/revoke` (normal web access cookie and existing origin protection)
- Extension-only initiation/exchange/status/submission: `POST /api/v1/extension/link-requests`, `POST /api/v1/extension/link-requests/:requestId/exchange`, `GET /api/v1/extension/status`, `POST /api/v1/extension/observations` (dedicated extension transport; status/submission require scoped bearer)
- Extension-owned watches: `GET /api/v1/extension/watches`, `PUT /api/v1/extension/watches`, `DELETE /api/v1/extension/watches/:watchId` (dedicated extension bearer; no web cookies)

The Prisma models include application authentication, shared canonical `Course`, `Group`, and `GroupStateChange` state, user-owned `Watch` rows, durable `Notification` rows, and one `EmailDelivery` outbox row per eligible notification; there is no per-scan observation table or inferred academic-term model. A watch references the internal canonical Group UUID and is unique per user/group. Unwatch hard-deletes the watch while past notification history remains. Repeated create/delete requests are idempotent; missing canonical groups are never fabricated. Responses join last-known shared state and omit Choose URLs. Observation ingestion accepts only the shared structured contract, never Classroom HTML or credentials. The API does not retain submitting-user identity on shared state. See the root README for the `UNKNOWN`/stale-update policy and extension boundary. Verification and reset emails link to the frontend origin configured by `CORS_ORIGIN`. `SMTP_USER` and `SMTP_PASSWORD` are optional as a pair for unauthenticated local SMTP servers. Docker Compose does not start an SMTP server. Configure the Google Cloud OAuth Web client and all four `GOOGLE_*` variables as described in the root README before starting the API.

## Notification email worker

Apply `20261011000000_notification_email_outbox` before starting a worker. In `apps/api/.env`, `NOTIFICATION_EMAIL_DELIVERY_ENABLED=false` is the safe default, including development and test. To test locally, start a **mail-capture sink** listening only on `localhost:1025`, keep `SMTP_HOST=localhost`, `SMTP_PORT=1025`, `SMTP_SECURE=false`, and leave `SMTP_USER`/`SMTP_PASSWORD` unset. Then deliberately set `NOTIFICATION_EMAIL_DELIVERY_ENABLED=true` and run `pnpm --filter api worker:dev` from the repository root; stop with Ctrl+C. The sink must not forward mail to the internet. Non-production validation rejects enabling this worker with a nonlocal SMTP host, a different port, TLS, or SMTP authentication. The ordinary API process does not schedule delivery. For deployment, apply migrations, configure production TLS-capable SMTP and `NOTIFICATION_EMAIL_DELIVERY_ENABLED=true`, build with `pnpm --filter api build`, and run `pnpm --filter api worker` as a separately supervised process; stop it with SIGTERM. Run one worker initially. Multiple workers safely claim different rows with PostgreSQL `FOR UPDATE SKIP LOCKED`.

Each process checks at most 10 jobs sequentially every 15 seconds, claiming each immediately before send with a two-minute lease. A crash leaves `PROCESSING` work reclaimable after the lease; five total attempts are allowed. Transient errors retry after exponential delays starting at one minute with up to 20% jitter; explicit SMTP 5xx rejection fails immediately. Exhausted jobs remain `FAILED` for operational inspection. Unique `notificationId` means one job per notification; its owner (`Notification.userId`) identifies the recipient without a duplicated address field. The outbox stores status, attempts, timestamps, a short-lived claim token, and a coarse failure category—never credentials, addresses, message bodies, or Classroom HTML. The recipient is re-read from the owning user and must still have a verified, valid BTU email. Deleted users cascade-delete their jobs. A sent email does not change notification `readAt`.

Delivery uses **bounded at-least-once attempts, not guaranteed or exactly-once receipt**: SMTP can accept a message just before the worker crashes, leaving the database unable to distinguish delivery from failure; a lease retry may send it again. An exhausted abandoned lease can likewise be marked failed even if SMTP accepted the last attempt. The additive migration deliberately does not backfill older notifications, including synthetic Phase 8A manual-test events. Diagnose `FAILED` rows operationally; there is no public arbitrary-send endpoint or automatic replay of terminal failures. Email delivery does not solve the separate Phase 7 question of observing Classroom while all student browsers are offline.

### Delivery operations (Phase 8C)

Apply `20261012000000_email_delivery_operations` and deploy the API build **before** restarting the independently supervised worker. There is no student- or extension-accessible operations endpoint. Run these commands only on a trusted deployment host with restricted shell access to `DATABASE_URL`; `--operator` is an audit label, not authentication. Do not paste database URLs, SMTP credentials, recipients, or email bodies into tickets or logs.

```sh
pnpm --filter api build
pnpm --filter api email-ops status
pnpm --filter api email-ops failed
pnpm --filter api email-ops failed --page 1
pnpm --filter api email-ops recover <job-uuid> --operator <operator-id> --ticket <ticket-id>
pnpm --filter api email-ops recover <job-uuid> --operator <operator-id> --ticket <ticket-id> --confirm
```

`status` returns aggregate counts for every delivery state, the age of the oldest **due** PENDING/RETRY job, expired PROCESSING lease count, counts of each job's latest failure category when its last attempt was within 24 hours, and a shared worker heartbeat. `failed` lists FAILED job IDs in bounded 20-row pages (`--page 0` by default) with coarse classifications and attempts, never addresses or content. Refresh pages after recovery because the result set can shift. The worker records startup and updates its shared completion heartbeat after every completed batch, including empty batches. `worker.stale=true` means no worker has completed a batch in 10 minutes (or none has ever done so); it detects a stopped or stalled delivery service, not which worker failed when several run. A disabled worker is expected to show stale. Also monitor each production process with its supervisor.

Suggested initial alerts while delivery is enabled: stale heartbeat, oldest due job age over 10 minutes, any expired lease persisting beyond its two-minute recovery window, a rising FAILED count, or sustained SMTP_TRANSIENT failures. Use these as operational starting points rather than delivery-time guarantees. The SMTP connection/greeting/socket inactivity limits are 10/10/20 seconds; they are shorter than the two-minute per-job lease, but a pathological peer or process pause can still outlast that lease and cause at-least-once duplicate delivery. The worker stops claiming on SIGTERM and finishes its current send before exit; configure a deployment termination grace period longer than an ordinary SMTP attempt and monitor lease expiry after hard kills.

For machine-readable JSON without pnpm's script banner, a trusted-host monitor can run `pnpm --filter api exec node dist/notifications/email-ops.js status` and inspect `worker.stale`, backlog age, lease count, and failure counts. Keep the monitor private and page an operator on the thresholds above; the CLI does not expose an HTTP metrics port. Worker warnings contain only a job UUID and coarse failure category or an expired-lease count, never SMTP error text or message contents.

Recovery is **dry-run by default**. Confirm the job ID from `failed`, investigate the failure and SMTP sink/provider first, then record a non-sensitive operator ID and incident/ticket ID. Only `--confirm` changes a still-FAILED job to RETRY. The CLI rechecks the owner's verified BTU email before requeueing; the worker checks again immediately before sending. Recovery is idempotent for the same ticket, creates an audit row with the prior attempt count/failure category, and permits at most two manual recovery cycles per job; each cycle still has at most five automatic send attempts. A SENT job is never replayed. Deleting a user/notification cascades its jobs and their recovery audit, consistent with the existing privacy lifecycle. Do not edit outbox rows directly.

For a safe local verification, use only a non-forwarding SMTP capture sink on localhost:1025 and synthetic watched groups. With delivery enabled, create a genuine FULL→AVAILABLE transition, run `status`, then confirm one captured mail and a SENT job without changing notification `readAt`. To exercise recovery without sending real email, stop the worker, use an isolated test database or local sink to produce a FAILED job, run the dry-run and confirmed commands, restart the worker, and confirm one audit row plus a SENT or bounded FAILED outcome. To roll back an unhealthy deployment, stop the worker and set `NOTIFICATION_EMAIL_DELIVERY_ENABLED=false`; leave outbox rows and the additive migration intact for later diagnosis/retry. The older API can ignore the new tables/column while the worker is disabled. Never point local synthetic tests at real outbound SMTP.

The extension authorization is separate from application cookies. A link request is valid for five minutes; approval requires a verified, signed-in user and the existing trusted web origin. Exchange requires a locally generated high-entropy verifier whose challenge hash is stored server-side, can be used only once, and issues a 90-day credential scoped to structured observation submission and that user's watches. The API stores only the credential hash, expiry, revocation, and last-used timestamp. A different origin is rejected when supplied; missing Origin is tolerated only on dedicated cookie-rejecting extension routes because browser/service-worker header behavior varies. Authentication never relies on Origin or extension ID alone. The normal `/observations` route still requires web cookies and its original CSRF policy. Deploy edge/IP rate limits for public link initiation and exchange endpoints.

Web logout revokes the web session, not a separately approved extension authorization. Use `/extension-link` to revoke the latter explicitly; uninstalling the extension alone does not revoke its server-side record.

PostgreSQL ingestion and extension lifecycle tests run only when `OBSERVATION_TEST_DATABASE_URL` points to a separately migrated database named `btu_course_watch_phase5a_test`; otherwise they are skipped. Create that database locally, apply migrations to it with `DATABASE_URL=<test-database-url> pnpm --filter api exec prisma migrate deploy`, then run `OBSERVATION_TEST_DATABASE_URL=<test-database-url> pnpm test`. Never point this variable at development or production data.
