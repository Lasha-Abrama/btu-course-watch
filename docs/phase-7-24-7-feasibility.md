# Phase 7: Feasibility of always-online course monitoring

Status: investigation only, updated 4 October 2026 with credential-safe manual observations. No BTU credential values, authenticated response bodies, or new production components were collected or added for this report. **Server-side 24/7 monitoring is no-go on current evidence.**

## What is established

Phase 6B is **best-effort browser-assisted monitoring**, not live or 24/7. Its MV3 alarm runs only when Chrome and the device can execute extension work and the student's BTU Classroom session remains valid. The service worker obtains the linked owner's watches through the scoped Course Watch extension credential, deduplicates course IDs, and fetches `/ge/student/me/course/index/{btuCourseId}` with `credentials: "include"`, `cache: "no-store"`, and `redirect: "manual"`. It parses that authenticated response locally for one unambiguous, same-course Groups anchor, follows the exact HTTPS Groups href, parses the Groups HTML locally, and submits **only** `CourseObservation` to the existing ingestion endpoint. The second Groups-path component (observed as `47`) remains opaque; it is not derived, interpreted, or stored. See `apps/extension/src/monitoring.ts`, `inspection.ts`, and `packages/classroom-parser/src/subject-page.ts`.

The user's live test proved this pipeline for courses `665` and `672` with Chrome running, the Mac awake, BTU tabs closed, and no manual Inspect: `2 of 2` observations submitted, and watched groups `13344` and `13490` advanced their canonical `Last observed` timestamps to 30 September 2026, 18:14:30. Earlier local tests showed authenticated subject-page `fetch()` responses for both courses contained their Groups anchors. Two consenting students saw the same Groups paths for these courses and the same nine displayed groups for `665` while selection was disabled. These observations **do not** establish that students see identical definitive `AVAILABLE`/`FULL` states when selection opens, nor do they show that a backend can authenticate independently of a browser.

The repository stores Course Watch accounts, scoped/revocable extension credentials, user-owned watches, and shared canonical group observations. It has no BTU credential or server-side BTU fetch model. Phase 5A accepts stale/duplicate observations safely and preserves a last-known definitive state when a later scan is `UNKNOWN`; this does not make stale data live. Chrome documents that alarms do not wake a sleeping device and that missed repeating alarms are not replayed one by one ([Chrome alarms API](https://developer.chrome.com/docs/extensions/reference/api/alarms)).

BTU publicly describes Classroom as its academic management and registration system ([BTU student map](https://btu.edu.ge/stsavla/map/)). A September 2026 BTU announcement says its separately operated mobility platform is directly integrated with Classroom and automatically retrieves certain verified academic data ([BTU mobility announcement](https://btu.edu.ge/en/btu-launches-integrated-digital-platform-for-international-mobility-management-btumobility-ge/)). This is a credible lead for asking BTU about an approved integration, **not** evidence of a public API, group-availability feed, third-party access, or permission to reuse student sessions. Targeted public searches found no Classroom-specific developer API documentation; absence from search is not proof that none exists.

The user reports BTU staff said no API is available. This is a **reported conversation, not written technical confirmation**; it does not rule out internal integrations such as the published mobility-platform connection or establish whether an approved project could use one.

## Unknowns that block a server design

- Which particular first-party cookies or other browser state make authenticated **read-only** subject/Groups GETs succeed? Both tested routes depended on included browser credentials, and the Groups document request carried a `Cookie` header. Classroom-scoped `argus_session` is the strongest observed session candidate based on its name and scope, **not** an isolated or proven sufficient credential. Ordinary browser headers and security-layer state may also matter. No visible `Authorization`, `X-CSRF-*`, `X-Requested-With`, or `Origin` header appeared on that document request. `PHPSESSID` and `ru_auth` belong to `rateuni.framework.ge`, not Classroom, and provide no evidence about Classroom authentication.
- How long is the effective BTU session valid, and does it renew or rotate? Authentication survived one regular Chrome quit/restart and roughly a day without intentional reauthentication while `argus_session` remained marked `Session`. A separate fresh Incognito login also showed `argus_session`; that Incognito session stayed authenticated across one Mac sleep/wake interval. None of this establishes an exact server-side lifetime, coverage of the selection period, or that `argus_session` alone suffices, and it does not show that a server could reproduce browser authentication. No token values should be compared, copied, or retained to answer this.
- Is there an underlying first-party Groups-data JSON/API endpoint? None was obvious in the initial Fetch/XHR inspection of course `665`; that does not prove none exists. Even if one exists, an authenticated endpoint is not automatically a supported or server-accessible integration.
- Can BTU legitimately issue a narrowly scoped, revocable read-only server credential or webhook, with renewal, rate limits, and terms permitting this use? Can it supply per-student availability where necessary?
- During an active selection window, can two students see different definitive availability or eligible groups for the same course? Shared canonical state and future alert semantics need this checked before relying on global equivalence.

## Controlled, credential-safe experiments

Use **only your own account or another student's account with explicit consent**, ordinary BTU UI, and one or two known courses. Avoid the active registration rush where possible. Inspect locally; report behavioral outcomes and metadata only. Never export HAR, use “Copy as cURL/fetch,” copy request/response bodies, share screenshots showing values, or save DevTools logs. In particular, never record or send passwords, Cookie/Set-Cookie values, CSRF values, Authorization values, provider tokens, or authenticated HTML. Clear the Network log when finished. Chrome documents where to view cookie attributes in [Application > Cookies](https://developer.chrome.com/docs/devtools/application/cookies) and request status, resource type, and header **names** in the [Network panel](https://developer.chrome.com/docs/devtools/network/reference/).

1. **Baseline request shape — initial check performed for `665`.** While signed in, open a subject normally, then its Groups tab. In DevTools Network, note only request method, first-party host, sanitized path _shape_ (`/course/index/{id}`, `/course/groups/{id}/{opaque}`), status, redirect destination _path shape_, response content type, and whether the request is Document or Fetch/XHR. For successful read-only GETs, record presence/absence of header **names** such as `Cookie`, `Authorization`, `X-CSRF-*`, `X-Requested-With`, `Origin`, `Referer`, and `Sec-Fetch-*`; do not record their values. Record whether any response sets cookies by **name and attributes only**. Repeat on `672` if useful. This identifies candidate browser dependencies but does not prove each header is mandatory.
2. **Cookie inventory without values — initial metadata inspected.** In Application > Cookies for the Classroom host, record each potentially relevant cookie's **name, domain, path, HttpOnly, Secure, SameSite, Expires/Max-Age (or Session), and partition key**. Do not copy or photograph the Value column. Compare before/after ordinary subject and Groups navigation: did names, expiry metadata, or `Set-Cookie` _names_ change? This suggests renewal but cannot establish secret-value rotation. Do not delete or reinsert cookies in your normal profile.
3. **Minimal credential-dependence check — performed for subject and Groups GETs on `665`.** From an authenticated Classroom tab, run a _read-only_ console test on a known subject URL; it reads neither headers nor body. The same test was also performed on the naturally observed Groups URL. Do not paste its output if it contains anything unexpected:

   ```js
   const path = "/ge/student/me/course/index/665";
   for (const credentials of ["include", "omit"]) {
     const response = await fetch(path, {
       credentials,
       cache: "no-store",
       redirect: "manual",
     });
     console.log({ credentials, status: response.status, type: response.type });
   }
   ```

   The observed `omit` redirect supports dependence on included browser credentials. The console test cannot isolate individual cookies or establish that browser-generated headers are unnecessary.

4. **Lifetime and restart — regular restart/overnight use and one fresh-Incognito sleep/wake checkpoint succeeded.** Without exporting browser state, record only whether the same read-only subject/Groups GET still works after longer idle intervals and through the selection period. One regular Chrome quit/restart succeeded without re-login, and roughly a day later normal authenticated use still worked without intentional reauthentication. After a separate fresh Incognito login, the window remained present through a Mac sleep/wake cycle; Classroom refresh still showed an authenticated user, and course `665` Groups opened without re-login. The sleep interval was not measured here. Continue passive observation toward a longer checkpoint, ideally about 24 hours from that fresh login if practical. Record check time, whether the Incognito session remained open, whether fresh login was required, and only relevant cookie **metadata** or `Set-Cookie` header names. [Chrome ends an Incognito session when all Incognito windows close](https://support.google.com/chrome/answer/95464); closing them would confound this lifetime test. Do not leave an automated probe running or infer unlimited validity from these observations. The repository cannot perform this authenticated test independently without deliberately receiving reusable BTU authentication material, which is out of scope.
5. **First-party data source — initial `665` inspection performed.** With DevTools Network filtered to Fetch/XHR, open Groups normally. Record whether a **first-party** request returns JSON or HTML, its method/status/content type and sanitized path template, and whether it shares the same authentication behavior. Do not inspect/copy payloads, invent endpoints, replay state-changing requests, or bypass controls. If no such request appears, record “none observed,” not “none exists.” Ignore unrelated extension-injected rating badges and requests; they are not Classroom data.
6. **Institutional route — informal staff report received; written technical inquiry open.** Ask BTU's academic-system/IT owner via [official contact channels](https://btu.edu.ge/en/kontaqti/). Send no browser captures or secrets. The concise technical questions are:
   - Is there an **approved read-only API or webhook** for course/group availability, and may third-party student tools use it?
   - Is delegated per-user authorization available? What scopes, renewal, expiry, and revocation mechanisms apply?
   - Is availability user-specific, and what polling frequency or rate limits are permitted?
   - Does the publicly described mobility-platform/Classroom integration use a mechanism available to approved projects? Its existence does **not** establish a public API.

   Only with BTU's approval should a separately scoped server-side proof of concept be considered.

If identifying a particular cookie becomes necessary, use a **disposable, consented test profile** and a separately approved protocol. One-at-a-time local deletion can invalidate the session and is not required for the initial decision; never transplant cookie values to a server to “test” them.

## Architecture options

| Approach                                          | Device offline?                               | Server authentication and recovery                                                                 | Feasibility/security judgment                                                                                                                                                                                |
| ------------------------------------------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| BTU-approved read-only API or webhook             | Can continue                                  | Institution-issued scoped server credential or signed push; documented renewal, revocation, limits | Preferred route to genuine continuity, **if BTU supports and authorizes it**; validate group/availability semantics.                                                                                         |
| BTU-approved per-user delegated authorization     | Can continue while grant is valid             | Narrow, revocable, renewable server grant; user consent and expiry handling                        | Possible if BTU explicitly offers it; outages/expired grants still require recovery. Do not assume Google or Course Watch login grants Classroom access.                                                     |
| Existing opt-in browser-assisted observations     | **No**                                        | No BTU material on our server; extension uses the student's browser session                        | Already working and lowest BTU-credential exposure, but cannot promise 24/7. Multiple consenting installations improve coverage, not a guarantee.                                                            |
| Reuse a student's Classroom session on our server | Technically could run while device is offline | Reusable session material would need transfer, high-risk storage, refresh/rotation and re-login    | **Not the default and no-go now.** Requires explicit later security/product and institutional authorization decisions; could expose the student's broader Classroom account. Do not implement as a shortcut. |

An underlying JSON endpoint alone changes the response format, **not** the authentication/authorization problem. Running a headless browser with student credentials or copying cookies to a server would cross the same prohibited boundary. A server process also needs capacity, rate limits, failure recovery, and BTU permission to provide a credible continuous service.

## Engineering paths without BTU secrets

**Already reusable:** `packages/contracts` defines serializable `CourseObservation`; `packages/classroom-parser` validates local subject-link discovery and Groups markup; the extension's 30-minute MV3 cycle fetches only in the user's browser and submits structured observations. The owner-scoped `GET /api/v1/extension/watches` supplies course/group targets. The scoped extension credential authorizes `POST /api/v1/extension/observations` without web cookies or Classroom material. The API's strict observation validation and `ObservationsService.ingest()` provide serializable, stale-safe, idempotent canonical updates and discovery/status-change history; `Watch` remains user-owned while `Course`/`Group` are currently shared. These pieces need no new credential collection.

**Only if BTU later approves server access:** a separate BTU integration adapter would need a documented read-only authorization boundary, approved scope and renewal/revocation, target selection and bounded scheduling, response-to-`CourseObservation` parsing, sanitized failure health, and rate-limit/backoff rules. It could reuse the observation contract, validation, and ingestion service, but **not** the extension's browser-cookie fetch path or its user bearer credential. Before a shared canonical feed or alerts, establish whether observations require a student/eligibility context; if so, the current globally keyed Course/Group state needs a deliberate data-model boundary. Do not scaffold any of these pieces before an approved mechanism and data semantics exist.

**Distributed opt-in browser observers:** consenting installations can already observe their owners' watched courses through Phase 6B and submit to Phase 5A; its timestamp/concurrency rules resolve duplicate or out-of-order submissions. This may improve coverage when some browsers are online, but it is **not 24/7** and must not imply a particular student's availability is globally true. Broader volunteer coverage would require explicit opt-in and scope decisions, not silent expansion of watch targets. If active-selection observations differ by student, do not merge them into one globally meaningful availability or build cross-user alerts on them.

## Active-selection cross-student comparison

Run only when selection is genuinely active, with **two consenting students** who can normally view the same course (preferably `665`) and without clicking Choose/enroll. Use separate, unlinked extension installations/profiles so local **Inspect** displays the parser result without submitting to the shared API; the existing linked popup would submit automatically. Do not capture or exchange HTML, cookies, headers, Google state, Choose URLs, screenshots, or personal identifiers.

1. Agree on the same course and a narrow time window. Each student opens that course's Groups tab through ordinary navigation. Confirm the exact supported Groups route and that the selection regime is active; all-`UNKNOWN` selection-disabled results are inconclusive.
2. Within roughly 30–60 seconds, each presses local Inspect and records only UTC observation time, `btuCourseId`, the set of `btuGroupId`s, and for each ID its `AVAILABLE`/`FULL`/`UNKNOWN` status, capacity, and **boolean** Choose-action presence. Optionally record a coarse, non-identifying eligibility category if both consent. Ignore unrelated extension-injected badges.
3. Compare by **group ID**, not position or count. If any definitive status or group set differs, repeat near-simultaneously twice to distinguish a rapid seat change from a stable context difference; never perform an enrollment action to test it. Agreement in a few scans is supporting evidence, not proof of global equivalence. A reproducible mismatch blocks global availability claims and requires user/eligibility-scoped canonical state before cross-user alerts.

No new Phase 7 implementation phase is recommended yet. The next steps are to continue the passive Incognito observation toward roughly 24 hours from fresh login if practical, conduct the consented active-selection comparison when that window opens, and seek written clarification from BTU about an authorized read-only integration. Server-side 24/7 prerequisites are not satisfied; browser-assisted monitoring already exists and needs no speculative extension of scope.

## Decision gate

**Go** for a separate server-side 24/7 implementation only after BTU confirms a legitimate server-accessible, read-only interface or narrowly scoped delegated grant and its permitted use; the team validates renewal/revocation and behavior throughout the roughly two-week selection period; per-student versus global availability semantics are measured during active selection; and a security/privacy review approves the exact server-held material, logging, retention, and failure handling. A tested endpoint that merely works with a copied student session is **not** sufficient. Until then, **no-go** for a server worker or BTU credential storage. Keep Phase 6B labeled best-effort browser-assisted monitoring, with last-observed timestamps and explicit session/device limitations. Notifications and enrollment remain outside this investigation.

No credential values or authenticated response bodies were collected for this update. The initial experiments above narrow the browser authentication model but do not change the no-go decision.
